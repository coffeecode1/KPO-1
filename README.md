# ВышКат

Консольное приложение на Go: приём транспорта через техосмотр, учёт вещей,
отчёты по количеству и энергии, список для новичков, инвентарный список.

## Запуск

```bash
go run .              # приложение (пункт 6 «Демо» показывает все сценарии)
go test -cover ./...  # тесты с покрытием (~93%)
```

## Структура

- `internal/domain` – модель. Интерфейсы `Inventoried` (название + инвентарный номер),
  `EnergyConsumer` (суточный расход), `Vehicle` (`Inventoried` + простота 1–10).
  Транспорт: `Scooter`, `Bicycle`, `ElectricBike`. Вещи: `Helmet`, `ChargingCabinet`, `DockStation`.
  Общие части `Item` и `Energy` встраиваются в типы (в Go вместо наследования).
- `internal/service` — `ServiceCenter` (интерфейс техосмотра) и `StandardServiceCenter`,
  `Park` (приём и хранение), `Report` (отчёты).
- `internal/di` — DI-контейнер на `go.uber.org/dig`.
- `internal/app` — консольное меню.

## Логика

- Транспорт попадает в парк только через `Park.AddVehicle`: проверка, что номер свободен и потом техосмотр. Вещи (`AddThing`) техосмотр не проходят.
- Техосмотр отклоняет, если номер <= 0, простота вне 1-10 или расход электротранспорта вне [0; 3] кВт*ч.
- Энергия суммируется по всем `EnergyConsumer` на балансе (транспорт и вещи).
- Для новичков – простота ≥ 6 (`service.MinBeginnerSimplicity`).

## SOLID

- **S** – каждый тип делает одно: `Park` хранит, `Report` считает, `StandardServiceCenter` проверяет, `App` общается с пользователем.
- **O** – новый вид транспорта = новый тип + строка в `app/kinds.go`; `Park` и `Report` не меняются.
- **L** – любой `Vehicle` одинаково принимается парком и учитывается в отчётах.
- **I** – маленькие интерфейсы: шлему нужен только `Inventoried`, лишних методов никто не реализует.
- **D** – `Park` зависит от интерфейса `ServiceCenter`, реализацию подставляет DI-контейнер.

## Ответы на вопросы

**Какой принцип применён наиболее явно?**
DIP: `service.NewPark(center ServiceCenter)` получает техосмотр снаружи, его выбирает
контейнер в `internal/di`. Поэтому в тестах техосмотр легко заменить.

**Какой принцип сознательно ограничен?**
DIP для `service.Report`: он зависит от конкретного `*Park`, а не от интерфейса.
Хранилище одно, и интерфейс ради одной реализации был бы «декоративным».

**Что сломается при расширении?**
- Новый вид транспорта: ничего. Тип в `domain` + строка в `vehicleKinds`.
- Сотрудник: ничего. Отдельный тип без `Inventoried`, на баланс попасть не может.
- Склад запчастей: отдельный сервис; если запчасти показывать в общем списке,
  нужна одна правка в `Report.Inventory`.

**Какие тесты фиксируют техосмотр и правило для новичков?**
- `service/park_test.go`: в `NewPark` передаётся заглушка `stubServiceCenter`;
  тесты проверяют, что парк принимает или отклоняет транспорт по её решению.
- `di/container_test.go`: `TestContainerServiceCenterCanBeReplaced` подменяет техосмотр
  прямо в контейнере через `Decorate`.
- `service/service_center_test.go`: правила настоящего техосмотра.
- `service/report_test.go`: `TestReportBeginnerVehiclesUsesThresholdSix` — простота 6 и 7 проходят, 5 нет.
